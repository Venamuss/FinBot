# FinBot

Текущий инкремент: React-панель управления семейными расходами (Slice 04), административный REST CRUD и Telegram-бот с LLM и PostgreSQL. Архитектура и дальнейшие этапы: [docs/architecture.md](docs/architecture.md), [docs/tasks.md](docs/tasks.md). Исходное ТЗ: [docs/test-task-expenses.md](docs/test-task-expenses.md); точный контракт: [docs/api.md](docs/api.md).

Панель показывает расходы всех участников, поддерживает комбинируемые фильтры, серверную сортировку и страницы, создание, редактирование и удаление с подтверждением. Интерфейс на русском, без авторизации. REST не требует авторизации и позволяет работать со всеми владельцами; Telegram allowlist к нему не применяется.

## Запуск

Требуются Docker Engine и Docker Compose v2+ с доступом к реестру образов, Go proxy, npm registry и Alpine packages.

```sh
cp .env.example .env
# Задайте в .env собственный POSTGRES_PASSWORD, затем:
docker compose up -d --build --wait
# Панель: http://127.0.0.1:8080
curl http://127.0.0.1:8080/api/expenses
```

Пароль для Compose должен состоять из URL-safe символов (буквы, цифры, `-`, `_`): он включается в URI подключения. `.env` не коммитится. Compose запускает `frontend` (React, собранный Vite и раздаваемый nginx), `app` (Go REST и Telegram) и `db`. nginx проксирует `/api` в Go с исходным Host: браузер работает с одним origin, CORS не нужен. Миграции встроены в Go-бинарник и выполняются через Goose до открытия HTTP-порта; каждая миграция и запись её версии применяются транзакционно. Повторный запуск не применяет завершённые миграции заново, одновременные запуски защищены advisory lock.

Compose ожидает готовности PostgreSQL, затем приложения, затем nginx. Внутренний `GET /readyz` приложения проверяет PostgreSQL с дедлайном 2 секунды: `204` при доступной БД, безопасный `503` при сбое. Проверка доступна после миграций и не проксируется nginx. Это readiness, а не liveness: сбой БД делает `app` unhealthy, но сам по себе не перезапускает контейнер. Healthcheck frontend проверяет раздачу страницы nginx. LLM и Telegram не входят в readiness: их недоступность не мешает панели. Проверить приложение внутри Compose: `docker compose exec -T app wget -q -O /dev/null http://127.0.0.1:8080/readyz`.

SQL-файлы в `backend/migrations/` используют числовые версии и секции `-- +goose Up` / `-- +goose Down`. Приложение автоматически выполняет только Up; Down первой миграции удаляет таблицу расходов. История Goose хранится в `goose_db_version`. При обновлении с прежнего runner начальная миграция сохраняет существующие `expenses`, индекс и данные через `IF NOT EXISTS`; прежняя `schema_migrations` остаётся нетронутой и больше не используется. Такой переход рассчитан на исходную схему FinBot, а не на вручную изменённые таблицы.

По умолчанию nginx доступен только на `127.0.0.1:8080`. `HTTP_PORT` меняет порт хоста; `HTTP_BIND_IP` меняет интерфейс публикации. Go и PostgreSQL не имеют опубликованных портов; данные находятся в именованном томе `postgres_data`. `docker compose down` сохраняет том; `docker compose down -v` удаляет данные. Изменение пароля в `.env` само по себе не меняет пароль уже созданной БД.

```sh
curl -i http://127.0.0.1:8080/api/expenses \
  -H 'Content-Type: application/json' \
  -d '{"user_id":"123456789","amount":"350.5","category":"еда","spent_at":"2026-10-16"}'
curl 'http://127.0.0.1:8080/api/expenses?user_id=123456789&sort=amount&order=asc&limit=10'
```

Суммы и ID передаются строками. Ответ нормализует сумму до двух знаков. Отсутствующий комментарий возвращается как `null`, пустая строка сохраняется. Даты календарные; временные метки возвращаются в UTC. Изменяющий запрос с `Origin` принимается только при совпадении со схемой и Host запроса. Reverse proxy должен сохранять исходный Host; доверие к `X-Forwarded-*` пока не настраивается.

## Панель и разработка frontend

Node.js 24 LTS и npm. Из `frontend/`:

```sh
npm ci
npm run dev
# http://127.0.0.1:5173
npm test
npm run typecheck
npm run build
```

Vite проксирует `/api` в локальный Go на `127.0.0.1:8080`, сохраняя Host для проверки Origin. Для работы с Compose достаточно запустить его на стандартном порту; отдельный Go-процесс не нужен. При другом порте API запустите `FINBOT_DEV_API_URL=http://127.0.0.1:PORT npm run dev` или задайте эту переменную в `frontend/.env.local`. Она используется только конфигурацией dev server; production-клиент обращается к относительному `/api`. В production Vite dev server не используется: Node собирает статику, nginx раздаёт `dist/` и проксирует запросы в `app:8080`. Переменные окружения бэкенда и секреты не включаются в frontend-сборку. Существующие `HTTP_PROXY`, `HTTPS_PROXY`, `NO_PROXY` передаются только Go-сервису.

В разделе «Участники семьи» можно добавить Telegram ID и задать или изменить отображаемое имя. Имена показываются в журнале расходов и фильтре; Telegram ID остаётся вторичной подписью. Без имени отображается ID. Для существующего участника ID изменить нельзя: переименование не меняет владельцев расходов или доступ к боту. Имена не загружаются из Telegram, могут совпадать, обрезаются по краям и ограничены 100 символами без управляющих символов. Пустое поле убирает имя. Участники с сохранёнными метаданными остаются в справочнике даже без расходов; новые владельцы расходов появляются автоматически без имени.

При создании расхода можно выбрать существующий ID или ввести новый. Пустой комментарий означает отсутствие комментария; редактирование сохраняет нетронутые `null` и пустые строки. PATCH отправляет только изменённые поля. Сумма вводится с точкой, остаётся десятичной строкой и отображается без валюты. Новая форма подставляет текущую календарную дату браузера; дату можно изменить. Фильтры и страницы выполняются сервером, изменение фильтров сбрасывает страницу. На узком экране таблица прокручивается горизонтально. Ошибки загрузки можно повторить; ошибка сохранения оставляет форму и введённые данные.

Тесты используют Vitest, Testing Library и jsdom с подменой `fetch`; они не обращаются к Telegram или LLM. Шрифт Cantarell поставляется локально вместе с OFL-лицензией, внешние шрифтовые запросы не выполняются. Токены и правила интерфейса: [DESIGN.md](DESIGN.md).

Имена хранятся отдельно в `member_names` (миграция 003), расходы при обновлении сохраняются. REST: `GET /api/members` возвращает `user_id` и nullable `display_name`; `PUT /api/members/{user_id}` принимает `{"display_name":"Анна"}` или `{"display_name":null}`. Существующий `.env` менять не требуется. Миграция применяется при запуске обновлённого Go-сервиса.

## Telegram и LLM

В `.env` задайте `TELEGRAM_BOT_TOKEN`, `TELEGRAM_ALLOWED_USER_IDS` (например, `101,202`) и настройки выбранного LLM: `LLM_BASE_URL`, `LLM_MODEL`, `LLM_API_KEY`, `LLM_TIMEOUT`. Пустой токен отключает polling. Пустой allowlist запрещает бот всем; некорректный непустой список останавливает запуск. Разрешены положительные десятичные ID без знака и ведущих нулей; пробелы вокруг элементов и повторы допустимы. Изменения настроек требуют перезапуска. Секреты не добавляйте в репозиторий.

Бот принимает личные текстовые сообщения; владелец определяется только по `message.from.id`. Примеры: «кофе 350», «такси 1200 вчера», «покажи траты за неделю», «сколько потратил на еду в этом месяце», «последнее было не 350, а 450», «удали такси». Неоднозначный выбор требует ответа текстом, например «вторая»; выбор можно отменить обычным сообщением. Относительные даты вычисляются по времени исходного сообщения в `TIME_ZONE` (по умолчанию `Europe/Moscow`).

«Мои траты», «мои расходы» и «покажи все расходы за сегодня» показывают свои расходы за сегодня во всех категориях. Если период для списка или суммы не указан, сервер использует сегодня по времени сообщения в `TIME_ZONE`. Бот запрашивает ровно один вызов инструмента (`tool_choice: "required"`, `parallel_tool_calls: false`); неиспользуемые фильтры списка и суммы передаются как `null`. Некорректный ответ модели или конфликтующие фильтры дают безопасную подсказку без изменения расходов.

LLM использует один OpenAI-совместимый endpoint без автоматического fallback. Значения по умолчанию Go и Compose: `https://openrouter.ai/api/v1`, `google/gemma-4-31b-it:free`, timeout `30s`. В `.env.example` модель явно переопределена на `openai/gpt-4.1-mini`; после копирования файла используется она. Пустой ключ допустим для локального сервера; для OpenRouter задайте свой ключ. Ошибка LLM возвращает безопасный ответ, повторить запрос можно новым сообщением. Проверка с настоящим Telegram и выбранным провайдером остаётся отдельным ручным шагом; автоматические тесты не требуют их ключей.

Контекст независим для каждого пользователя, истекает после 30 минут бездействия и теряется при перезапуске. Повторный `update_id` возвращает сохранённый ответ без повторного изменения; ответ и изменение фиксируются одной транзакцией. Миграция 002 добавляет `telegram_updates`. Таблица содержит ответы бота, поэтому резервные копии БД содержат данные расходов. Сетевые запросы не выполняются внутри транзакций.

Ограничения: один процесс long polling; запросы обрабатываются последовательно. В списке показываются первые 20 записей и общее количество; при более чем 10 кандидатах бот просит уточнить описание. Поиск описания — буквальная подстрока комментария без учёта регистра. Комментарии в ответах сокращаются до 60 символов. Telegram-запрос имеет не более трёх попыток; при недоступности БД или отправки ответа polling повторяет неподтверждённое сообщение после паузы. При неоднозначном сетевом результате ответ может прийти повторно, но расход не изменится дважды. Постоянная ошибка отправки приостанавливает очередь до восстановления; долговечный outbox и очистка истории результатов не реализованы.

## Конфигурация и диагностика (Slice 04.5)

Backend читает окружение один раз через `internal/config`. Go-процесс не читает `.env` автоматически: экспортируйте переменные в shell; Compose читает `.env` и передаёт перечисленные настройки приложению. Некорректная настройка останавливает запуск до сетевых запросов; сообщение указывает имя переменной без её значения. `DATABASE_URL` обязателен и проверяется парсером pgx; `HTTP_ADDR` требует host и числовой порт 1–65535. Пустой токен и пустой ключ LLM остаются допустимыми по правилам выше.

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `LOG_LEVEL` | `INFO` | `DEBUG`, `INFO`, `WARN`, `ERROR`, регистр не важен |
| `HTTP_REQUEST_TIMEOUT` | `5s` | Дедлайн REST-операции при медленной БД; положительное Go duration меньше фиксированного HTTP write timeout `15s` |
| `STARTUP_TIMEOUT` | `30s` | Общий бюджет ожидания БД и миграций, для медленного диска/запуска |
| `TELEGRAM_HTTP_TIMEOUT` | `40s` | Общий HTTP timeout одной Telegram-попытки; должен превышать long poll |
| `TELEGRAM_POLL_TIMEOUT` | `25s` | Long poll, целые секунды от `1s` до `50s` |
| `TELEGRAM_RETRY_DELAY` | `1s` | Базовая задержка API retry, затем удвоенная; максимум три попытки, переполнение duration запрещено |
| `TELEGRAM_POLL_RETRY_DELAY` | `5s` | Пауза перед повтором неподтверждённого update или неудачного poll |

Все длительности положительные, например `500ms`, `30s`, `1m30s`; дробные секунды недопустимы только для long poll. Уже существующие `LLM_BASE_URL`, `LLM_MODEL`, `LLM_API_KEY`, `LLM_TIMEOUT`, `TIME_ZONE`, Telegram token/allowlist, `HTTP_BIND_IP` и `HTTP_PORT` сохраняются. Параметры соединения/пула PostgreSQL задаются через `DATABASE_URL` (например, `connect_timeout` и `pool_max_conns`); отдельные дублирующие настройки не добавлены. В стандартном Compose DSN формируется из `POSTGRES_PASSWORD`; другой PostgreSQL/пул можно задать через Compose override. `HTTP_PROXY`, `HTTPS_PROXY`, `NO_PROXY` продолжают использовать стандартный Go transport; прокси-адреса не логируются.

JSON-логи идут в stdout через `log/slog`. DEBUG содержит технические события начала запросов, пустых poll, readiness и безопасных transaction diagnostics; INFO — запуск/остановку и завершённые операции; WARN — отказ доступа, ошибки валидации и повторы; ERROR — неуспешные операции. Ошибки БД/HTTP не форматируются в логи: используются фиксированные `error_category` (`timeout`, `network`, `rate_limit`, `api`, `protocol`, `validation`, `database`, `deadlock`, `serialization_failure`, `application` и другие локальные категории). Обычная отмена при остановке не считается ошибкой Telegram/LLM.

События содержат `component`, `operation`, `duration_ms` и доступные протокольные поля: `http_status`, `attempt`, `update_id`, известное имя `tool`, `tool_call_count`, LLM `model`. HTTP пишет одно событие на запрос с локальным `request_id` и шаблоном маршрута; ID уникален только в пределах процесса, входящий `X-Request-ID` не копируется. Telegram update ID передаётся в conversation/LLM/transaction events. При корректных данных провайдера LLM completion содержит `prompt_tokens`, `completion_tokens`, `total_tokens` и latency; отсутствующие/некорректные usage не считаются нулевой стоимостью. Денежная стоимость не вычисляется: тариф зависит от провайдера.

Токены, ключи, заголовки, DSN, полные внешние URL, сообщения пользователей, prompts, ответы модели, tool arguments, комментарии и имена участников не логируются даже при DEBUG. SQL/expense service не пишут отдельные дублирующие события на каждый запрос: результат виден на границе HTTP/Telegram; transaction retry имеет отдельную безопасную диагностику. nginx сохраняет отключённые access logs. В Docker context исключены вложенные `.env*`; Vite не получает backend-секреты через `define` или `VITE_*`.

## Разработка и проверки

[GitHub Actions CI](.github/workflows/ci.yml) запускается при push в `master` и pull request в `master`, с правом `contents: read`:

- `backend`: Go из `backend/go.mod` (сейчас 1.27.1), кеш модулей/сборки, проверка gofmt, `go vet` и `go test -race ./... -count=1 -timeout=180s`. PostgreSQL 17 работает в отдельном service container; `TEST_DATABASE_URL` задан обязательно. Весь набор включает миграции и Telegram pipeline с mock HTTP-сервисами.
- `frontend`: Node.js 24, кеш npm, `npm ci` по lockfile, Vitest и `npm run build` (включает `typecheck`). Календарные тесты дополнительно работают в `America/Los_Angeles` и `Pacific/Kiritimati`. Lint-скрипта в проекте нет; новый инструмент не добавлен.
- `containers`: валидация Compose, сборка обоих production-образов, запуск с healthchecks, REST smoke и проверка сохранности после restart и пересоздания контейнеров. Используются отдельный проект/том, синтетический пароль, пустой Telegram token и недоступный тестовый LLM URL; ключи, VPN и прокси разработчика не нужны. Тестовый том удаляется при завершении job.

Наличие workflow не означает успешный прогон на GitHub: его результат нужно проверить после push/PR. Локально workflow можно проверить через `actionlint .github/workflows/ci.yml`, если actionlint установлен.

Go 1.27.1 или новее; прямые зависимости — `pgx/v5` для PostgreSQL и `goose/v3` для миграций. Goose использует адаптер `database/sql` поверх существующего `pgxpool`, отдельный драйвер БД не добавляется. Из `backend/`:

```sh
gofmt -w cmd internal migrations
go test ./...
go vet ./...
DATABASE_URL='postgres://user:password@host:5432/finbot?sslmode=disable' go run ./cmd/finbot
```

`DATABASE_URL` обязателен. `HTTP_ADDR` по умолчанию `127.0.0.1:8080`; Compose задаёт `:8080` внутри контейнера. Запуск ожидает БД и применяет миграции в пределах общего `STARTUP_TIMEOUT` (по умолчанию 30 секунд); при неуспехе процесс завершается до приёма запросов. SIGTERM/SIGINT останавливают HTTP с ожиданием активных запросов до 10 секунд, отменяют Telegram polling и внешние запросы; после остановки обработчиков закрывается пул БД.

Без `TEST_DATABASE_URL` тесты PostgreSQL и Telegram pipeline явно пропускаются. Для полной проверки задайте адрес отдельной тестовой PostgreSQL и выполните из `backend/` (race detector требует CGO и C-компилятор):

```sh
TEST_DATABASE_URL='postgres://user:password@host:5432/testdb?sslmode=disable' \
  go test -race ./... -count=1 -timeout=180s
```

Тестовый пользователь должен иметь право создавать схемы. Тесты создают отдельные случайные схемы и удаляют только их. Проверяются чистое и повторное применение миграций, одновременный запуск Goose, переход с прежней схемы с сохранением расходов и Down/Up в изолированной тестовой схеме. Существующие таблицы не очищаются. Адрес БД Compose можно использовать из Go-контейнера в той же сети без публикации PostgreSQL. Например, из корня проекта для стандартного имени Compose-проекта `finbot` (замените `test-password` на пароль тестовой установки):

```sh
docker run --rm --network finbot_default \
  -v "$PWD/backend:/src" -w /src \
  -e 'TEST_DATABASE_URL=postgres://finbot:test-password@db:5432/finbot?sslmode=disable' \
  golang:1.27.1-alpine go test ./internal/postgres -run Integration -count=1 -v
```

HTTP smoke использует Python 3.9+ без дополнительных пакетов. Запускайте его только на тестовой установке: он оставляет четыре синтетических расхода и две записи метаданных участников для проверки сохранности. Из корня репозитория:

```sh
python3 scripts/smoke.py --state-file /tmp/finbot-smoke.json
docker compose restart
python3 scripts/smoke.py --state-file /tmp/finbot-smoke.json --verify
docker compose down
docker compose up -d --wait
python3 scripts/smoke.py --state-file /tmp/finbot-smoke.json --verify
```

Для другого HTTP-порта передайте `--url http://127.0.0.1:PORT`. Скрипт проверяет создание, чтение, комбинируемые фильтры, сортировку, страницы, форматы и ошибки. Повторный `--verify` проверяет записи после перезапуска и пересоздания контейнеров с сохранённым томом. Результаты проверок текущего инкремента и ограничения среды записаны в [docs/tasks.md](docs/tasks.md).
