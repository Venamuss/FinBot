# Требования FinBot

Источник обязательных требований — [исходное тестовое задание](test-task-expenses.md). Ниже отдельно описаны требования ТЗ, проектные требования текущего запроса и допущения реализации. Этапы находятся в [tasks.md](tasks.md), устройство приложения — в [architecture.md](architecture.md), точный REST-контракт — в [api.md](api.md).

## Обязательные требования исходного ТЗ

Идентификаторы R01–R14 относятся только к ТЗ. Критерии показывают, как проверить соответствующее обязательство; технические способы реализации и трактовки вынесены в проектные решения.

| ID | Требование ТЗ | Критерий приёмки |
|---|---|---|
| R01 | Модель расхода | Сохраняются `id`, Telegram `user_id`, `amount`, `category`, `spent_at`, необязательный `comment`, `created_at`, `updated_at`. Категории: еда, транспорт, жильё, развлечения, здоровье, покупки, другое |
| R02 | Добавление через бота | Обычный текст, включая «кофе 350» и «такси 1200 вчера», сохраняется как расход с автоматически определёнными суммой, категорией и датой |
| R03 | Просмотр через бота | Поддержаны «покажи траты за неделю» и «сколько потратил на еду в этом месяце»: пользователь получает свои расходы или их сумму за нужный период |
| R04 | Изменение через бота | Пользователь может изменить свою трату естественным языком, включая пример «последнее было не 350, а 450» |
| R05 | Удаление через бота | Пользователь может удалить свою трату естественным языком, включая пример «удали такси» |
| R06 | Изоляция пользователей | Через бота нельзя прочитать, посчитать, изменить или удалить чужие расходы |
| R07 | Естественный язык | CRUD бота проходит без кнопок и команд |
| R08 | Список в панели | Панель показывает расходы всех участников; фильтры по владельцу, периоду и категории работают отдельно и совместно |
| R09 | CRUD в панели | Можно создавать, просматривать, изменять и удалять расходы всех участников |
| R10 | REST API | Веб-панель взаимодействует с backend через REST |
| R11 | Go backend | Бэкенд написан на Go; конкретный frontend-стек ТЗ не устанавливает |
| R12 | Compose | Приложение запускается со своими зависимостями через один `docker compose` |
| R13 | Конфигурируемый LLM | Доступ к LLM задаётся через конфигурацию |
| R14 | Панель без авторизации | Для работы с панелью не нужен вход |

## Проектные требования и допущения

«Текущий запрос» означает явно заданную пользователем корректировку. «Проектный выбор» означает способ реализации или трактовку, а не дополнительное требование исходного ТЗ.

| ID | Решение | Основание |
|---|---|---|
| P01 | Модульный монолит Go, PostgreSQL, REST, React/TypeScript, Telegram и LLM tool calling | Архитектурная основа текущего запроса |
| P02 | Конфигурируемый allowlist Telegram ID; без разрешения бот не выполняет операции. Отдельной таблицы пользователей нет | Текущий запрос |
| P03 | Один OpenAI-compatible adapter. Для MVP достаточно проверить один настроенный endpoint; локальный LLM — необязательная дополнительная проверка | Текущий запрос |
| P04 | Фокус диалога имеет приоритет; без фокуса используется последняя созданная собственная запись. Несовпадение названной старой суммы требует уточнения | Текущий запрос |
| P05 | Точные JSON-контракты, ошибки, фильтры, пагинация и сортировка описаны в [api.md](api.md); ID и суммы передаются строками | Текущий запрос и проектные значения по умолчанию |
| P06 | Go обслуживает React, REST и бот; Compose запускает приложение и PostgreSQL. Панель предназначена для доверенной локальной сети | Проектный выбор |
| P07 | Суммы положительные, с точностью до сотых, без `float`. Валюта не хранится, не отображается и не конвертируется | Проектный выбор |
| P08 | Часовой пояс по умолчанию — `Europe/Moscow`, настраиваемый. Относительные даты считаются от времени Telegram-сообщения; границы фильтров включены | Проектный выбор |
| P09 | Контекст хранится в памяти отдельно по пользователям и истекает через 30 минут бездействия; неоднозначные действия требуют текстового уточнения | Проектный выбор |
| P10 | Одна семья на установку, участники обозначаются Telegram ID. Поддерживаются личные текстовые сообщения; одно обращение изменяет одну трату | Проектный выбор |
| P11 | В панели можно менять владельца, сумму, категорию, дату и комментарий. ID и временные метки формирует сервер | Проектный выбор |
| P12 | Постоянный том, автоматические миграции, транзакционная защита от повторной доставки и серверная проверка инструментов LLM | Проектный выбор для корректности и безопасности |

## Allowlist бота

- `TELEGRAM_ALLOWED_USER_IDS` содержит положительные Telegram ID через запятую. Пробелы вокруг элементов допускаются, повторы удаляются.
- Отсутствующее или пустое значение запрещает бот всем; панель продолжает работать. Некорректный непустой список считается ошибкой конфигурации при запуске.
- Список загружается при запуске; изменение требует перезапуска. Формат подробно задан в [architecture.md](architecture.md).
- Проверка по `message.from.id` выполняется до LLM, чтения сохранённого результата сообщения и операций с расходами. Пользователь вне списка получает общий отказ без раскрытия данных.
- Разрешение пользоваться ботом не даёт доступа к чужим расходам. Каждый запрос по-прежнему ограничен собственным `user_id`.
- Allowlist не ограничивает REST панели и назначение владельца в панели. Записи с владельцем вне списка допустимы, но этот владелец не может работать с ботом до получения разрешения.

## Даты и диалог

- Без даты используется сегодняшний день в настроенном часовом поясе относительно исходного сообщения.
- «За неделю» — сегодня и шесть предыдущих дней; «на этой неделе» — с понедельника по сегодня; «в этом месяце» — с первого числа по сегодня.
- Фокус устанавливается после создания, изменения или однозначного выбора собственной траты. Выборка из нескольких записей сама по себе не выбирает одну; удаление выбранной траты очищает фокус.
- При отсутствии фокуса, включая истечение контекста или перезапуск, «последняя трата» — собственная запись по `created_at DESC, id DESC`, независимо от `spent_at`.
- Если собственных расходов нет, бот сообщает об этом без изменения данных.
- Если названа старая сумма, она сравнивается с фактической до изменения; при несовпадении бот уточняет намерение.
- Если существующий фокус устарел из-за изменения, удаления или передачи записи через панель, бот уточняет намерение без скрытого переключения на другую запись.
- Перед отложенным изменением владелец и актуальность записи проверяются атомарно с записью.
- При нескольких совпадениях, например «удали такси», до текстового уточнения ничего не меняется. Недостающую обязательную информацию бот также спрашивает текстом.

## LLM и критерий MVP

Один адаптер настраивается через `LLM_BASE_URL`, `LLM_MODEL`, необязательный `LLM_API_KEY` и `LLM_TIMEOUT`. Для MVP нужны автоматические проверки контракта и ручной прогон одного настроенного endpoint с поддержкой tool calling.

Локальный сервер можно подключить тем же способом, но его реальная проверка дополнительная и не блокирует MVP. Автоматического перехода в облако нет. Сервер модели предоставляется отдельно; установка моделей и управление GPU в проект не входят.

MVP готов, когда проверены R01–R14 и обязательные проектные правила, проходят сценарии безопасности, воспроизводится запуск и описаны ограничения. Локальный прогон не входит в обязательный критерий сдачи. Задачи и проверки находятся в [tasks.md](tasks.md).

## Риски и границы

| Риск | Решение и оставшееся ограничение |
|---|---|
| Панель не проверяет личность главы семьи | Любой с сетевым доступом к панели или API может работать со всеми расходами; allowlist бота этого не меняет |
| Ошибка настройки allowlist | Пустой список запрещает бот всем, неверный непустой список останавливает запуск; изменение требует перезапуска |
| Доступность внешних сервисов | Трактовка запуска: Compose поднимает приложение и БД; Telegram и настроенный LLM endpoint предоставляются отдельно |
| Совместимость модели | Поддержка обычной генерации текста недостаточна; у выбранной модели проверяется tool calling |
| Локальный endpoint не проверен | Это известный статус дополнительной проверки, а не причина отклонять готовый MVP |
| Ошибки и вредоносные инструкции LLM | Сервер проверяет аргументы и владельца; модель не получает административные инструменты или SQL |
| Потеря контекста | После перезапуска применяется явно заданный выбор последней созданной собственной записи; старая сумма проверяется до изменения |
| Повторная доставка и устаревшие данные | Результат и изменение фиксируются одной транзакцией; отложенная операция повторно проверяет владельца и актуальность |
| Изменения во время просмотра страниц | Offset-пагинация допускает смещение строк между запросами; стабильная сортировка не создаёт снимок данных |
| Передача данных провайдеру | Отправляются только необходимые данные текущего пользователя, без общей семейной выборки и секретов; автоматического перехода между серверами нет |

Не добавлять авторизацию панели, несколько семей, роли, приглашения, бюджеты, графики, экспорт, чеки, голосовые сообщения, повторяющиеся расходы или мультивалютность. Любое расширение требует отдельного обоснования.
