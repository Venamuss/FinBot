# Этапы реализации FinBot

Основание: [требования ТЗ и проектные решения](requirements.md), [архитектура](architecture.md), [REST-контракт](api.md). Текущий этап — только документация; код приложения начинается отдельным заданием.

R01–R14 обозначают требования исходного ТЗ, P01–P12 — проектные решения, T01–T13 — задачи реализации и проверки. Контракты описаны в документах; задачи разработки ниже пока не выполнены. Завершение задачи отмечать вместе с фактическим результатом и выполненными проверками.

## Обязательный MVP

Все задачи T01–T12 обязательны. Независимые ветки можно вести в любом порядке после готовности указанных зависимостей.

| ID | Этап | Зависимости | Критерий завершения |
|---|---|---|---|
| T01 | Зафиксировать REST-контракт и проверить один настроенный LLM endpoint | Документы | Проверены примеры контракта; прямой пробный запрос подтверждает tool calling выбранной модели. Производственный адаптер для этого прогона ещё не требуется |
| T02 | Реализовать правила сумм, категорий и дат | Контракт | Проверены денежная точность, календарные периоды и валидация |
| T03 | Добавить миграции и PostgreSQL-операции | T02 | CRUD, фильтры, суммы, выбор последней собственной записи и ограничения владельца проверены на PostgreSQL |
| T04 | Подготовить конфигурацию, сборку и Compose | Контракт | Приложение и БД запускаются; миграции и постоянный том работают; задан формат allowlist и настроек LLM |
| T05 | Реализовать REST API | T03 | JSON, обязательность и nullable-поля, PATCH, ошибки, фильтры, сортировка и пагинация соответствуют [api.md](api.md) |
| T06 | Подключить Telegram, allowlist и защиту от повторов | T03 | Личные сообщения принимаются; запрещённый ID не достигает LLM, сохранённых ответов или операций с расходами; повторный `update_id` не повторяет изменение |
| T07 | Реализовать configurable OpenAI-compatible adapter | T01, T02 | Проверены аргументы инструментов, настройки, необязательный ключ, тайм-ауты, некорректные ответы и отсутствие автоматического перехода на другой endpoint |
| T08 | Реализовать диалоговый CRUD | T06, T07 | Проходят примеры ТЗ, выбор по фокусу, последняя созданная собственная запись без фокуса, проверка старой суммы и текстовые уточнения |
| T09 | Проверить доступ и безопасность | T05, T08 | Проверки разрешённых A/B, запрещённого C, чужих ID, независимости контекстов и устаревших записей проходят |
| T10 | Реализовать React-панель | REST-контракт; для интеграции T05 | Работают список, фильтры, сортировка, страницы и CRUD |
| T11 | Проверить панель в браузере | T10 | Проверены основные действия, пустые состояния, ошибки API и безопасный вывод текста |
| T12 | Выполнить сквозную приёмку и подготовить инструкцию | T01–T11 | Воспроизводимы чистый Compose, перезапуск, сценарии двух разрешённых пользователей и отказ запрещённому; работает один настроенный LLM endpoint; ограничения описаны |

Frontend можно начинать по [api.md](api.md) на тестовых ответах; сдаваемое приложение обязательно проверяется с реальным REST.

## Критический путь

- Подготовка данных: T02 → T03; проверка LLM: T01 → T07.
- Эти ветки сходятся с Telegram-транспортом T06 в T08, затем проходят обязательную проверку безопасности T09 и сквозную приёмку T12.
- REST и панель образуют параллельную обязательную ветку: T03 → T05 → T10 → T11 → T12.
- Конфигурация и Compose T04 нужны для итогового запуска. Дополнительная T13 не входит в критический путь и не является зависимостью T12.

## Дополнительная проверка

| ID | Проверка | Условие | Результат |
|---|---|---|---|
| T13 | Реальный прогон локального LLM через тот же адаптер | После готовности MVP, при наличии сервера и подходящей модели | Зафиксированы сервер, модель, доступность из Docker, поддержка инструментов и результаты CRUD. Отсутствие или неуспех проверки не блокирует MVP |

Для локального прогона проверить пустой ключ, корректный адрес из контейнера, тайм-аут и отсутствие обращений к облачному провайдеру. Сервер модели предоставляется отдельно; установка моделей и управление GPU не являются задачами проекта.

## Обязательные тестовые сценарии

| Группа | Проверка и ожидаемый результат | Связь с требованиями |
|---|---|---|
| Модель | Все поля и категории, необязательный комментарий; системные поля защищены от записи клиентом | R01, P11 |
| Деньги | `0.10 + 0.20 = 0.30`; ноль, отрицательные суммы, превышение диапазона и лишние десятичные знаки отклоняются без округления | R01–R04, R09, P07 |
| Даты | Московская полночь, границы месяца и года, високосный день, последние семь дней; границы фильтров включены, перевёрнутый интервал отклоняется | R02, R03, R08, P08 |
| Бот | Все примеры ТЗ; изменение категории, даты и комментария; пустые результаты; недостающая информация вызывает уточнение | R02–R05, R07, P09 |
| Allowlist | Разрешены A/B, запрещён C; пустая конфигурация запрещает всем при работающей панели; некорректный непустой список — ошибка запуска; пробелы и повторы обрабатываются по контракту | P02 |
| Порядок допуска | C не вызывает LLM, не читает сохранённый результат и не выполняет операции с расходами. Удаление ID из списка с перезапуском блокирует и повтор ранее обработанного сообщения | P02, P12 |
| Изоляция A/B | Чужой известный ID недоступен для чтения, изменения и удаления; списки, суммы, последняя запись и кандидаты A не раскрывают B; изменённых чужих строк нет | R06, P02 |
| Подмена полномочий | ID в тексте, заявление об административных правах, пересланный текст и поддельные аргументы LLM не меняют владельца и разрешение | R06, P02, P12 |
| Последняя трата | Актуальный фокус имеет приоритет; без фокуса выбирается собственная запись по `created_at DESC, id DESC`, независимо от даты покупки; проверены равные `created_at`, отсутствие расходов и восстановление после потери контекста | R04, P04, P09 |
| Старая сумма | Совпадение позволяет изменение; несовпадение вызывает уточнение и не меняет запись, как с фокусом, так и без него | R04, P04 |
| Уточнения | Контексты A/B независимы; несколько такси вызывают вопрос без удаления; «вторая» выбирает только предложенного собственного кандидата | R04–R06, P09 |
| Устаревшая запись | Изменение, удаление или передача владельца через панель не приводит к выполнению старого отложенного действия; другой расход скрыто не выбирается | R04–R06, R09, P04, P11 |
| JSON и CRUD REST | ID и суммы — строки; обязательные поля, `null`, пустой комментарий, пропущенные поля PATCH и очистка комментария работают по контракту; системные и неизвестные поля отклоняются | R09, R10, P05, P11 |
| Ошибки REST | Проверены статусы и коды из [api.md](api.md), единый объект ошибки, отсутствие внутренних подробностей, `Allow` при неподдерживаемом методе и `204` без тела при удалении | R10, P05 |
| Фильтры и страницы | Каждый фильтр и сочетания через AND, включённые границы, значения по умолчанию и границы `limit`/`offset`, точный `total`, пустые выборки и страницы; неизвестные, пустые и повторные параметры отклоняются | R08, R10, P05 |
| Сортировка | Разрешённые поля и направления; числовой порядок ID и сумм; устойчивый порядок равных значений по `id`; неизвестное поле отклоняется | R10, P05 |
| Участники и владельцы | Справочник содержит уникальных владельцев существующих расходов и не равен allowlist; панель создаёт запись для нового ID и меняет владельца; без разрешения бот этого владельца запрещён | R06, R09, R14, P02, P11 |
| Повторная доставка | Один `update_id` изменяет данные один раз, включая повтор после фиксации и перезапуска; одинаковый текст с разными ID создаёт отдельные расходы | R02, R04, R05, P12 |
| Адаптер LLM | Один настроенный endpoint проходит реальный прогон; автоматические проверки покрывают конфигурацию, пустой ключ, неправильную модель, отсутствие tool calling, некорректный JSON, неизвестную операцию и тайм-аут | R13, P03 |
| Сбои | Ошибка БД откатывает изменение и результат; ошибка LLM до выполнения не приводит к записи; ошибка отправки ответа не повторяет изменение; другой endpoint автоматически не вызывается | P03, P12 |
| Инъекции | SQL-подобный текст остаётся данными; HTML и скрипты выводятся текстом; инструкции в комментариях не дают новых полномочий | R06, R10, P12 |
| Браузер | CRUD, фильтры, сортировка и страницы работают; пустые результаты и сетевые ошибки понятны; неуспешное сохранение не показывается как успешное | R08–R10, P05 |
| Запуск | Чистый Compose после настройки конфигурации, повторные миграции, сохранность расходов после перезапуска; панель работает при пустом allowlist и недоступном LLM | R11–R14, P01–P03, P06, P12 |

Автоматические сценарии используют подмену LLM и Telegram; SQL и транзакции проверяются на PostgreSQL. Обязательный ручной прогон использует один настроенный LLM endpoint, двух разрешённых Telegram-пользователей и одного запрещённого. Отдельный реальный локальный прогон учитывается только в T13.

## Готовность MVP

- R01–R14 и обязательные проектные правила проверены; результаты T01–T12 отмечены в этом документе.
- Проходят примеры задания, allowlist, изоляция собственных расходов и сценарии последней траты.
- REST и панель соответствуют [api.md](api.md).
- Выполнены проверки Go, проверка типов и сборка frontend; проходит Compose smoke.
- Инструкция запуска воспроизводима, описывает конфигурацию allowlist и выбранного LLM endpoint, ограничения сети и потерю контекста.
- Статус T13 указан отдельно: не выполнена, пройдена или не пройдена. Любой из этих статусов допустим для сдачи MVP.
- Ограничения и оставшиеся риски описаны. Процент покрытия сам по себе не является критерием готовности.
