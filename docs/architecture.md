# Архитектура FinBot

Основа — модульный монолит Go, PostgreSQL, REST, React/TypeScript и Telegram с LLM tool calling. Обязательства ТЗ и проектные решения разделены в [requirements.md](requirements.md); этапы находятся в [tasks.md](tasks.md).

## Компоненты

```text
Браузер ── React + REST ──► Go-приложение ──► PostgreSQL
                                  │
Telegram ◄── long polling ────────┤
                                  └──────► Настроенный LLM API
```

Два обязательных сервиса Compose: приложение и PostgreSQL. Go обслуживает собранный React, REST API и цикл Telegram-бота. Frontend собирается отдельным этапом Docker-сборки; дополнительный веб-сервер не требуется.

Long polling позволяет принимать сообщения без публичного входящего адреса. См. [Telegram Bot API: getUpdates](https://core.telegram.org/bots/api#getupdates).

Внутри Go разделить HTTP-обработчики, Telegram-обработчик, адаптер LLM, операции с расходами и PostgreSQL-запросы. Использовать `net/http`, `pgx` и обычный SQL. Не вводить микросервисы, брокер, Redis, ORM или отдельный агентный фреймворк.

## Данные

Основная таблица — `expenses`:

| Поле | Хранение и правило |
|---|---|
| `id` | Генерируемый положительный `BIGINT`, не изменяется клиентом |
| `user_id` | Положительный Telegram ID, `BIGINT` |
| `amount` | `NUMERIC(14,2)`, строго больше нуля |
| `category` | Текст с ограничением на семь значений из ТЗ |
| `spent_at` | `DATE` |
| `comment` | Необязательный текст |
| `created_at`, `updated_at` | `TIMESTAMPTZ`, формируются сервером; изменение записи обновляет `updated_at` |

Добавить индекс по владельцу и дате. Удаление физическое. Отдельной таблицы пользователей нет.

В Go суммы обрабатываются в целых сотых, без `float`. Избыточные десятичные знаки отклоняются без скрытого округления. Форматы JSON и допустимые значения определены в [api.md](api.md).

Служебная таблица обработанных Telegram-сообщений хранит уникальный `update_id` и результат. Она нужна для защиты от повторных изменений, а не для хранения переписки.

## REST и панель

Точные тела запросов и ответов, nullable-поля, ошибки, фильтры, пагинация и сортировка описаны только в [REST-контракте](api.md). Панель использует CRUD `/api/expenses` и справочный `/api/members`.

Проектный выбор: в панели редактируются владелец, сумма, категория, дата и комментарий. В форме создания разрешён ручной ввод Telegram ID нового участника. `/api/members` возвращает владельцев существующих расходов; это подсказка для формы и фильтра, а не реестр доступа и не содержимое allowlist.

Панель показывает список, комбинируемые фильтры, сортировку, страницы и формы CRUD. React и API работают с одного origin. Комментарии выводятся как текст.

Панель и REST не требуют авторизации и доступны всем клиентам в доверенной локальной сети. Allowlist бота не ограничивает REST или выбор владельца в панели.

## Конфигурация допуска к боту

`TELEGRAM_ALLOWED_USER_IDS` — список положительных Telegram ID через запятую. Каждый элемент после удаления окружающих пробелов должен быть десятичным ID от `1` до `9223372036854775807`, без знака и ведущих нулей. Повторы удаляются.

| Состояние конфигурации | Поведение |
|---|---|
| Переменная отсутствует, пуста или содержит только пробелы | Бот запрещён всем, панель работает |
| Непустой корректный список | Бот доступен только перечисленным ID |
| Некорректный непустой список, включая пустые элементы между запятыми | Ошибка конфигурации при запуске |

Список читается при запуске; изменение требует перезапуска. Динамическое управление участниками, wildcard и таблица пользователей не добавляются.

Проверять `message.from.id` до LLM, чтения сохранённого ответа и любых операций с расходами. Не использовать ID из текста, пересланного сообщения или аргументов модели. Отсутствие разрешения даёт общий отказ без данных расходов. Разрешение пользоваться ботом не отменяет ограничение каждого запроса собственным владельцем.

## LLM adapter

Один адаптер использует OpenAI-совместимый `/chat/completions` с function calling. Конфигурация:

| Настройка | Назначение |
|---|---|
| `LLM_BASE_URL` | Адрес API, включая `/v1`; может указывать на облачный или локальный сервер |
| `LLM_MODEL` | Выбранная модель с поддержкой инструментов |
| `LLM_API_KEY` | Необязательный ключ; при пустом значении заголовок авторизации не отправляется. Ключ задаётся, если его требует провайдер |
| `LLM_TIMEOUT` | Тайм-аут запроса, настраиваемый с учётом выбранного endpoint |

Для MVP обязательны автоматические проверки адаптера и реальный прогон одного настроенного endpoint с tool calling. Локальный сервер можно подключить тем же адаптером; его реальная проверка — дополнительная задача и не блокирует MVP.

Пример дополнительной проверки — Ollama с моделью, поддерживающей инструменты. Совместимость проверяется фактически: сервер поддерживает лишь часть API. См. [документацию Ollama](https://docs.ollama.com/api/openai-compatibility).

Сервер модели предоставляется отдельно. Для локального сервера нужен адрес, доступный из контейнера приложения; `localhost` внутри контейнера не обозначает хост. При выполнении дополнительной проверки описать подключение к хосту на Linux и доступность из Docker-сети.

Выбирается один endpoint. Автоматического переключения между локальным и облачным сервером нет. Нативные API отдельных провайдеров, установка моделей и управление GPU не добавляются.

LLM предлагает структурированное действие; исполняет его приложение. См. [официальную документацию function calling](https://developers.openai.com/api/docs/guides/function-calling).

## Обработка Telegram-сообщения

1. Получить личное текстовое сообщение и установить владельца по `message.from.id`.
2. Проверить allowlist. При отказе не обращаться к LLM, сохранённому результату или расходам.
3. Для разрешённого пользователя проверить повторную доставку по `update_id`.
4. Передать LLM текст, опорную дату и минимальный контекст этого пользователя.
5. Получить одно структурированное действие: создание, список, сумма, изменение, удаление либо уточнение.
6. Проверить аргументы, владельца, выбранную запись и названную старую сумму; выполнить операцию Go-кодом.
7. Зафиксировать изменение и результат обработки одной транзакцией; сформировать ответ из фактических данных.

Контекст в памяти содержит выбранную трату и незавершённое уточнение отдельно для каждого пользователя. Уточнение может сохранять недостающие поля либо набор собственных кандидатов. Контекст истекает через 30 минут бездействия; постоянная история диалога не нужна.

## Выбор последней траты

1. При наличии актуального фокуса использовать выбранную собственную запись.
2. Если фокуса нет, в том числе после истечения контекста или перезапуска, искать собственную запись по `created_at DESC, id DESC`. Дата покупки `spent_at` не определяет последнюю созданную запись.
3. При отсутствии своих записей сообщить об этом без изменения данных.
4. Если пользователь указал старую сумму, сравнить её с фактической до изменения. При несовпадении запросить уточнение.
5. Если существующий фокус устарел из-за изменения, удаления или передачи записи через панель, запросить уточнение без скрытой замены выбранной траты.

Проверка владельца и актуальности по `updated_at` выполняется атомарно с изменением. Общие календарные и диалоговые правила находятся в [requirements.md](requirements.md).

## Инварианты доступа и записи

- `user_id` отсутствует в аргументах инструментов модели: его добавляет сервер.
- Принимаются только известные операции и поля. LLM не получает произвольный SQL, HTTP-запросы или административные инструменты.
- Все операции бота, включая суммы, выбор последней записи и поиск кандидатов, ограничены владельцем.
- Изменение и удаление проверяют `id` вместе с `user_id` непосредственно в SQL.
- Отсутствующая и чужая запись дают одинаковый результат «не найдена».
- Уточнение выбирает запись только из предложенных собственных кандидатов.
- Изменение расхода и сохранение результата обработки Telegram-сообщения выполняются одной транзакцией. Повторная доставка разрешённому пользователю возвращает сохранённый результат без повторного изменения.
- Успех подтверждается после фиксации; ошибка отправки ответа не повторяет изменение.
- Бот использует внутренние операции Go, а не открытый REST API панели.

## Запуск и эксплуатация

- Публикуется только HTTP-порт приложения в доверенной локальной сети. PostgreSQL остаётся внутри Compose и использует именованный том.
- Миграции применяются до запуска обработчиков.
- Кроме LLM и allowlist, конфигурируются подключение к БД, Telegram-токен, часовой пояс и HTTP-порт.
- Секреты хранятся в `.env`; `.env.example` содержит только шаблоны.
- Внешние запросы ограничены тайм-аутами. Сбой LLM не мешает работе панели.
- Ошибка LLM до выполнения операции не меняет расходы. Уже зафиксированный результат не выполняется повторно.
- SQL параметризован; произвольный CORS не включается. Изменяющие запросы принимают JSON и проверяют `Origin`, если он присутствует; несовместимый origin отклоняется по [api.md](api.md).
- Эти проверки не заменяют авторизацию: API доступен любому клиенту в принятой сетевой границе.
- Достаточно проверки доступности приложения и БД и структурированных журналов без ключей, полного текста переписки и содержимого расходов.
