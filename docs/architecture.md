# FinBot Architecture

The foundation is a modular Go monolith, PostgreSQL, REST, React/TypeScript, and Telegram with LLM tool calling. Assignment obligations and project decisions are separated in [requirements.md](requirements.md); stages are in [tasks.md](tasks.md).

## Components

```text
Браузер ── React + REST ──► Go-приложение ──► PostgreSQL
                                  │
Telegram ◄── long polling ────────┤
                                  └──────► Настроенный LLM API
```

Two Compose services are mandatory: the application and PostgreSQL. Go serves the built React application, REST API, and Telegram bot loop. The frontend is built in a separate Docker build stage; no additional web server is required.

Long polling receives messages without a public inbound address. See [Telegram Bot API: getUpdates](https://core.telegram.org/bots/api#getupdates).

Within Go, separate HTTP handlers, the Telegram handler, the LLM adapter, expense operations, and PostgreSQL queries. Use `net/http`, `pgx`, and plain SQL. Do not introduce microservices, a broker, Redis, an ORM, or a separate agent framework.

## Data

The main table is `expenses`:

| Field | Storage and rule |
|---|---|
| `id` | Generated positive `BIGINT`; cannot be changed by the client |
| `user_id` | Positive Telegram ID, `BIGINT` |
| `amount` | `NUMERIC(14,2)`, strictly greater than zero |
| `category` | Text restricted to the seven values from the assignment |
| `spent_at` | `DATE` |
| `comment` | Optional text |
| `created_at`, `updated_at` | `TIMESTAMPTZ`, generated by the server; changing a record updates `updated_at` |

Add an index on owner and date. Deletion is physical. There is no separate users table.

In Go, amounts are processed as integer hundredths, without `float`. Excess decimal places are rejected without silent rounding. JSON formats and allowed values are defined in [api.md](api.md).

An auxiliary table of processed Telegram messages stores a unique `update_id` and the result. It prevents duplicate changes rather than storing conversation history.

## REST and Panel

Exact request and response bodies, nullable fields, errors, filters, pagination, and sorting are documented only in the [REST contract](api.md). The panel uses CRUD `/api/expenses` and the lookup endpoint `/api/members`.

Project choice: the panel edits the owner, amount, category, date, and comment. The creation form allows manual entry of a new member's Telegram ID. `/api/members` returns owners of existing expenses; it provides suggestions for the form and filter, rather than an access registry or the allowlist contents.

The panel provides a list, combinable filters, sorting, pagination, and CRUD forms. React and the API share the same origin. Comments are rendered as text.

The panel and REST API require no authentication and are available to all clients on the trusted local network. The bot allowlist does not restrict REST or owner selection in the panel.

## Bot Access Configuration

`TELEGRAM_ALLOWED_USER_IDS` is a comma-separated list of positive Telegram IDs. After trimming surrounding whitespace, each entry must be a decimal ID from `1` to `9223372036854775807`, without a sign or leading zeros. Duplicates are removed.

| Configuration state | Behavior |
|---|---|
| The variable is missing, empty, or contains only whitespace | Bot access is denied to everyone; the panel works |
| A valid non-empty list | Bot access is available only to the listed IDs |
| A malformed non-empty list, including empty entries between commas | Startup configuration error |

The list is read at startup; changes require a restart. Do not add dynamic member management, wildcards, or a users table.

Check `message.from.id` before calling the LLM, reading a stored response, or performing any expense operation. Do not use an ID from message text, a forwarded message, or model arguments. Lack of permission produces a generic denial without expense data. Permission to use the bot does not remove the requirement to scope every query to its owner.

## LLM adapter

A single adapter uses the OpenAI-compatible `/chat/completions` endpoint with function calling. Configuration:

| Setting | Purpose |
|---|---|
| `LLM_BASE_URL` | API address, including `/v1`; may point to a cloud or local server |
| `LLM_MODEL` | Selected model with tool support |
| `LLM_API_KEY` | Optional key; when empty, no authorization header is sent. Set a key if the provider requires one |
| `LLM_TIMEOUT` | Request timeout, configurable for the selected endpoint |

Slice 03B defaults are `https://openrouter.ai/api/v1`, `google/gemma-4-31b-it:free`, an empty key, and `30s`. Set these environment variables directly for a Go process or in `.env` for Compose. The base URL must be absolute HTTP(S), include the provider's API prefix, and contain no credentials, query, or fragment; the adapter appends `/chat/completions`. The timeout uses a positive Go duration such as `30s` or `1m30s`. Changing the endpoint or model requires configuration only. Model availability and tool support still require the T01 live check.

`internal/llm.New(configuration.LLM)` constructs a reusable client without network access. `Complete(ctx, llm.Request{...})` sends system/user messages, function definitions with JSON Schema parameters, and optional `ToolChoice` (`json.RawMessage`: `"auto"`, `"none"`, `"required"`, or a named function object). `RequireExactlyOneToolCall` validates the returned count locally. Responses contain nullable text, tool IDs/names with argument objects as `json.RawMessage`, and the finish reason. Unknown tool names and argument fields are left to the caller's business validation; no tool is executed here. Text with `length` or `content_filter` must be handled as incomplete/filtered by the caller; tool calls with those reasons are rejected.

Responses are limited to 1 MiB after HTTP decompression. Malformed envelopes, missing required fields, invalid argument JSON, inconsistent finish reasons, and duplicate tool IDs fail without exposing partial results. Standard extra metadata is ignored. HTTP errors expose a status code and fixed error category; transport errors expose only cancellation, deadline expiry, or a generic network failure. Provider bodies, URLs, headers, and keys are never included in returned errors or logged. Redirects are rejected, and there are no retries or automatic endpoint/model fallbacks. The client is not yet called by application request handling; Telegram integration belongs to later slices.

The MVP requires automated adapter checks and a live run against one configured endpoint with tool calling. A local server can use the same adapter; live verification is an additional task and does not block the MVP.

An example of an additional check is Ollama with a model that supports tools. Compatibility is verified in practice: the server supports only part of the API. See the [Ollama documentation](https://docs.ollama.com/api/openai-compatibility).

The model server is provided separately. A local server needs an address reachable from the application container; `localhost` inside the container does not refer to the host. When performing the additional check, document connectivity to the host on Linux and reachability from the Docker network.

One endpoint is selected. There is no automatic switching between local and cloud servers. Do not add provider-specific native APIs, model installation, or GPU management.

The LLM proposes a structured action; the application executes it. See the [official function calling documentation](https://developers.openai.com/api/docs/guides/function-calling).

## Telegram Message Processing

1. Receive a private text message and identify the owner using `message.from.id`.
2. Check the allowlist. On denial, do not access the LLM, stored result, or expenses.
3. For an allowed user, check for duplicate delivery using `update_id`.
4. Send the text, reference date, and minimal context for this user to the LLM.
5. Receive one structured action: create, list, total, update, delete, or clarify.
6. Validate the arguments, owner, selected record, and stated previous amount; execute the operation in Go.
7. Commit the change and processing result in one transaction; construct the response from actual data.

In-memory context contains the selected expense and a pending clarification separately for each user. A clarification may retain missing fields or a set of the user's own candidates. Context expires after 30 minutes of inactivity; persistent conversation history is not required.

## Selecting the Last Expense

1. If there is a current focus, use the selected record belonging to the user.
2. If there is no focus, including after context expiration or a restart, find the user's own record using `created_at DESC, id DESC`. The purchase date `spent_at` does not determine the most recently created record.
3. If the user has no records, report this without changing any data.
4. If the user stated a previous amount, compare it with the actual amount before making a change. Ask for clarification on a mismatch.
5. If an existing focus becomes stale because the record was changed, deleted, or reassigned through the panel, ask for clarification without silently replacing the selected expense.

Ownership and record freshness based on `updated_at` are checked atomically with the change. General calendar and conversation rules are in [requirements.md](requirements.md).

## Access and Write Invariants

- `user_id` is absent from model tool arguments: the server supplies it.
- Accept only known operations and fields. The LLM has no arbitrary SQL, HTTP requests, or administrative tools.
- All bot operations, including totals, last-record selection, and candidate searches, are scoped to the owner.
- Updates and deletes check `id` together with `user_id` directly in SQL.
- A missing record and another user's record produce the same «не найдена» result.
- Clarification selects a record only from the proposed candidates belonging to the user.
- Changing an expense and saving the Telegram message processing result occur in one transaction. Duplicate delivery to an allowed user returns the stored result without repeating the change.
- Success is confirmed after commit; failure to send a response does not repeat the change.
- The bot uses internal Go operations rather than the panel's open REST API.

## Startup and Operations

- Publish only the application's HTTP port on the trusted local network. PostgreSQL stays within Compose and uses a named volume.
- Apply migrations before starting the handlers.
- In addition to the LLM and allowlist, configure the database connection, Telegram token, time zone, and HTTP port.
- Store secrets in `.env`; `.env.example` contains templates only.
- Bound external requests with timeouts. An LLM failure does not prevent the panel from working.
- An LLM error before execution does not change expenses. A committed result is not executed again.
- Parameterize SQL; do not enable unrestricted CORS. Mutating requests accept JSON and check `Origin` when present; an incompatible origin is rejected according to [api.md](api.md).
- These checks do not replace authentication: the API is available to any client within the accepted network boundary.
- Application and database availability checks and structured logs without keys, full conversation text, or expense contents are sufficient.
