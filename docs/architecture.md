# FinBot Architecture

The foundation is a modular Go monolith, PostgreSQL, REST, React/TypeScript, and Telegram with LLM tool calling. Assignment obligations and project decisions are separated in [requirements.md](requirements.md); stages are in [tasks.md](tasks.md).

## Components

```text
Браузер ──► nginx (React, /api proxy) ──► Go-приложение ──► PostgreSQL
                                             │
Telegram ◄── long polling ────────────────────┤
                                             └──────► Настроенный LLM API
```

Slice 04 uses three Compose services: `frontend` (nginx serving the Vite production build and proxying `/api`), `app` (the Go REST API and Telegram loop), and PostgreSQL. This replaces the earlier project choice to serve React directly from Go: a small reverse proxy keeps the backend unchanged and provides same-origin access without CORS. Node is used only in a frontend Docker build stage; the runtime contains static files and nginx. Only nginx publishes a port, bound to localhost by default. Go and PostgreSQL remain private to the Compose network. Existing optional HTTP_PROXY, HTTPS_PROXY, and NO_PROXY settings remain on the Go service.

Long polling receives messages without a public inbound address. See [Telegram Bot API: getUpdates](https://core.telegram.org/bots/api#getupdates).

Within Go, separate HTTP handlers, the Telegram handler, the LLM adapter, expense operations, and PostgreSQL queries. Use `net/http`, `pgx`, and plain SQL. Do not introduce microservices, a broker, Redis, an ORM, or a separate agent framework.

## Data

The main table is `expenses`:

| Field | Storage and rule |
|---|---|
| `id` | Generated positive `BIGINT`; cannot be changed by the client |
| `user_id` | Positive Telegram ID, `BIGINT` |
| `amount` | `NUMERIC(14,2)`, strictly greater than zero |
| `category` | Text restricted to the seven values from the assignment |
| `spent_at` | `DATE` |
| `comment` | Optional text |
| `created_at`, `updated_at` | `TIMESTAMPTZ`, generated by the server; changing a record updates `updated_at` |

Add an index on owner and date. Deletion is physical. There is no authentication/users table. Optional display names live in `member_names` (migration 003), keyed by the immutable positive Telegram `user_id`, with a nullable name of at most 100 Unicode characters. No foreign key or ownership dependency is introduced into expenses. This metadata is an explicitly requested extension; names never determine authorization.

In Go, amounts are processed as integer hundredths, without `float`. Excess decimal places are rejected without silent rounding. JSON formats and allowed values are defined in [api.md](api.md).

An auxiliary table of processed Telegram messages stores a unique `update_id` and the result. It prevents duplicate changes rather than storing conversation history.

## REST and Panel

Exact request and response bodies, nullable fields, errors, filters, pagination, and sorting are documented only in the [REST contract](api.md). The panel uses CRUD `/api/expenses` and the lookup endpoint `/api/members`.

Project choice: the panel edits the owner, amount, category, date, and comment. The creation form allows manual entry of a new member's Telegram ID. `/api/members` returns the union of expense owners and saved name metadata, using a LEFT JOIN to retain unnamed owners discovered through Telegram. It provides suggestions for the form and filter, rather than an access registry or the allowlist contents. `PUT /api/members/{user_id}` atomically upserts only display_name; names are trimmed/validated in the service and may repeat. Clearing a name stores null and retains the ID metadata. No expense row, ownership predicate, Telegram transaction, or allowlist check changes.

The panel uses React/TypeScript, Vite, native fetch, and plain CSS. Local component state is sufficient; no router, component library, or global state dependency is needed. A small typed client follows the documented API envelopes, with string IDs/amounts and structured field errors. Filtering, sorting, and offset pagination run on the server. Requests superseded by filter changes are canceled/ignored. A changed query resets pagination; deletion of a page's last record moves to the preceding valid page.

Editing loads the current expense through GET, then sends only changed fields through PATCH. Unchanged null/empty comments are preserved; clearing text sends null. Amount validation/formatting uses string operations, IDs use exact BigInt range validation, and calendar dates are not converted between time zones for display. The create form defaults to today in the browser's local calendar. Native modal dialogs provide keyboard focus containment and confirmation; failed writes retain entered values.

React and the API share the same origin. nginx preserves the original Host including port for Go's Origin validation; it delegates the JSON body limit and API errors to Go. The Vite development proxy also preserves Host. Comments and member names are rendered as React text. A native details section manages names; named expense owners have a secondary ID label, and select option values remain exact string IDs. Fonts are self-hosted; frontend builds contain no environment secrets. Vitest/Testing Library/jsdom tests mock fetch, while real API/browser checks use a disposable Compose installation.

The panel and REST API require no authentication and are available to all clients on the trusted local network. The bot allowlist does not restrict REST or owner selection in the panel.

## Bot Access Configuration

`TELEGRAM_ALLOWED_USER_IDS` is a comma-separated list of positive Telegram IDs. After trimming surrounding whitespace, each entry must be a decimal ID from `1` to `9223372036854775807`, without a sign or leading zeros. Duplicates are removed.

| Configuration state | Behavior |
|---|---|
| The variable is missing, empty, or contains only whitespace | Bot access is denied to everyone; the panel works |
| A valid non-empty list | Bot access is available only to the listed IDs |
| A malformed non-empty list, including empty entries between commas | Startup configuration error |

The list is read at startup; changes require a restart. Do not add dynamic member management, wildcards, or a users table.

Check `message.from.id` before calling the LLM, reading a stored response, or performing any expense operation. Do not use an ID from message text, a forwarded message, or model arguments. Lack of permission produces a generic denial without expense data. Permission to use the bot does not remove the requirement to scope every query to its owner.

## LLM adapter

A single adapter uses the OpenAI-compatible `/chat/completions` endpoint with function calling. Configuration:

| Setting | Purpose |
|---|---|
| `LLM_BASE_URL` | API address, including `/v1`; may point to a cloud or local server |
| `LLM_MODEL` | Selected model with tool support |
| `LLM_API_KEY` | Optional key; when empty, no authorization header is sent. Set a key if the provider requires one |
| `LLM_TIMEOUT` | Request timeout, configurable for the selected endpoint |

Go and Compose defaults are `https://openrouter.ai/api/v1`, `google/gemma-4-31b-it:free`, an empty key, and `30s`. The `.env.example` template explicitly selects `openai/gpt-4.1-mini`, overriding the model fallback when copied. Set these environment variables directly for a Go process or in `.env` for Compose. The base URL must be absolute HTTP(S), include the provider's API prefix, and contain no credentials, query, or fragment; the adapter appends `/chat/completions`. The timeout uses a positive Go duration such as `30s` or `1m30s`. Changing the endpoint or model requires configuration only. Current model availability and tool support require live verification; the historical T01 result is recorded in [tasks.md](tasks.md).

`internal/llm.New(configuration.LLM)` constructs a reusable client without network access. `Complete(ctx, llm.Request{...})` sends system/user messages, function definitions with JSON Schema parameters, and optional `ToolChoice` (`json.RawMessage`: `"auto"`, `"none"`, `"required"`, or a named function object). `RequireExactlyOneToolCall` validates the returned count locally. Responses contain nullable text, tool IDs/names with argument objects as `json.RawMessage`, and the finish reason. Unknown tool names and argument fields are left to the caller's business validation; no tool is executed here. Text with `length` or `content_filter` must be handled as incomplete/filtered by the caller; tool calls with those reasons are rejected.

The conversation orchestrator sends `tool_choice: "required"` and `parallel_tool_calls: false`, retaining local count validation. The adapter's optional `ParallelToolCalls` pointer preserves omission for other callers. List/total tools use strict schemas with all filter keys required and nullable; their category/period enums also permit null. The server accepts omitted filters for compatible endpoints and rejects unknown fields/types and conflicting relative/explicit dates. Missing dates leave lists unbounded by date; totals retain the default of today from the message timestamp and configured time zone. List tools also accept nullable string `limit` (1–20, default 20) and `offset` (0–2147483647, default 0). Per-owner in-memory listing context exposes resolved filters and the next offset to the model for explicit follow-ups only; independent lists reset filters and pagination. Responses identify actual filters, counts and positions, fit Telegram's 4096 UTF-16-unit limit, and advance the next offset only by displayed rows. SQL keeps `spent_at DESC, id DESC` and owner scoping. One list call covers all categories when category is null or omitted. Rejected responses retain only validated finish reason and call count in `ResponseError` diagnostics; conversation events identify known tools and rejection stages without argument values.

Responses are limited to 1 MiB after HTTP decompression. Malformed envelopes, missing required fields, invalid argument JSON, inconsistent finish reasons, and duplicate tool IDs fail without exposing partial results. Standard extra metadata is ignored. HTTP errors expose a status code and fixed error category; transport errors expose only cancellation, deadline expiry, or a generic network failure. Provider bodies, URLs, headers, and keys are never included in returned errors or logged. Redirects are rejected, and there are no retries or automatic endpoint/model fallbacks. Slice 03C invokes the client from `internal/conversation` after Telegram authorization and duplicate lookup, before opening the expense/result transaction.

The MVP requires automated adapter checks and a live run against one configured endpoint with tool calling. A local server can use the same adapter; live verification is an additional task and does not block the MVP.

An example of an additional check is Ollama with a model that supports tools. Compatibility is verified in practice: the server supports only part of the API. See the [Ollama documentation](https://docs.ollama.com/api/openai-compatibility).

The model server is provided separately. A local server needs an address reachable from the application container; `localhost` inside the container does not refer to the host. When performing the additional check, document connectivity to the host on Linux and reachability from the Docker network.

One endpoint is selected. There is no automatic switching between local and cloud servers. Do not add provider-specific native APIs, model installation, or GPU management.

The LLM proposes a structured action; the application executes it. See the [official function calling documentation](https://developers.openai.com/api/docs/guides/function-calling).

## Telegram Message Processing

1. Receive a private text message and identify the owner using `message.from.id`.
2. Check the allowlist. On denial, do not access the LLM, stored result, or expenses.
3. For an allowed user, check for duplicate delivery using `update_id`.
4. Send the text, reference date, and minimal context for this user to the LLM.
5. Receive one structured action: create, list, total, update, delete, clarify, answer a pending field, select a displayed expense, or explicitly cancel a pending request. The server exposes tools appropriate to the current state and checks dispatch independently of the model.
6. Validate the arguments, owner, selected record, and stated previous amount; execute the operation in Go.
7. Commit the change and processing result in one transaction; construct the response from actual data.

Telegram replies are rendered deterministically by `internal/botresponse`, a pure presentation package depending only on expense result types. The transport sends `parse_mode: HTML`; all dynamic text is escaped before insertion. Confirmations normally occupy three lines: heading with ID, comment/category label with bold amount, and category/date metadata. Lists put one expense per line, group adjacent rows by calendar date without sorting again, and use a single blank line between groups. Their header combines the actual count and filters; pagination positions and the continuation hint appear only for a partial page. Pagination advances only by complete rendered entries. Money uses string grouping and a decimal comma (no floating point), with ₽ as the requested display convention. Russian date labels include the year; confirmations and selection prompts abbreviate month names. Summary counts/category breakdowns are omitted because the existing total query supplies only a sum; no decorative queries are added.

Comments are used as expense labels, falling back to the category for absent/blank comments; label whitespace is normalized to keep one logical line and long labels wrap naturally in Telegram. Comments that fit are displayed completely. Lists first defer whole records to the next page rather than shorten their labels. If one record cannot fit alone, or the bounded candidate list exceeds the message budget, labels receive an ellipsis and an explicit note that the full text is in the panel. Filter descriptions over 512 UTF-16 units also carry an explicit shortening label. These are presentation limits only; stored expense data stays intact. The message budget is 4096 visible UTF-16 units after HTML entity parsing, with fixed fields and the shortening notice reserved before assigning the remaining space to labels. Summary/empty/error responses have no blank separator lines.

New stored replies carry an internal `finbot:html:v1` prefix in the existing text column; orchestration removes it on delivery and escapes older plain-text replies, including on replay. Storage transactions and ownership predicates are unchanged. A handler failure sends a generic waiting notice while retaining the error and retry semantics, without claiming that a mutation failed or succeeded. Denial delivery is best-effort. After a committed result, explicit HTTP/API 400 or 403 send rejections are logged and acknowledged so later updates can proceed. Network errors, 429, 5xx and unclassified failures retain retries; bounded request retries and the polling delay honor valid `retry_after`/`Retry-After` guidance. An uncommitted handler error remains retryable even if delivering its notice fails permanently. See the [Telegram HTML rules](https://core.telegram.org/bots/api#html-style), [message limit](https://core.telegram.org/bots/api#sendmessage), and [retry parameters](https://core.telegram.org/bots/api#responseparameters).

In-memory context contains the selected expense and one pending state separately for each user. Pending state is explicitly a field clarification (`amount`, `category`, `spent_at`, `currency`, `target`, `request`), a displayed expense selection, or a previous-amount confirmation. Field clarifications retain the intended create/update operation, validated known values, original request and calendar reference; selections retain only the user's own candidates and deferred operation. Only selection/confirmation states expose `choices` and `choose_expense`. Scalar field replies use `answer_clarification`, and the server applies the value only to the actual expected field. A category reply cannot select a record or retarget an update.

Deletion additionally uses `delete_confirmation`: resolving a unique target or selecting a candidate stores exactly that expense and its `updated_at`, and renders a yes/no question. The model has no confirmation tool. Standalone affirmative replies are routed by Go directly to the pending action; only this state can call the owner-scoped delete. A bare affirmative without a confirmation is read-only, and `нет` declines pending work. Cancellation is intercepted before model planning, including from idle. All pending decisions have a fixed 30-minute deadline checked again inside the transaction after planning; rejected replies cannot extend it. Deletion after panel modification/deletion/reassignment fails the existing atomic SQL version/owner guard and clears the obsolete confirmation.

Go checks explicit read/edit/delete intent against the proposed tool, validates the user's displayed choice against the model's ordinal, binds explicit `#ID` references and `не X, а Y` amounts to the source, checks monetary values against source price tokens, and rejects unrequested update fields. Explicit complete edits/deletions supersede pending work even if the model omits `request_context=new`. General interpretation stays in the configured LLM; unusual phrasing and amounts written as words can require a clearer numeric request. No state-machine framework, schema, dependency or transport/domain coupling was introduced.

New creations default to independent requests; other independent mutations or field clarifications use `request_context=new` (explicit complete edit/delete commands are also recognized by Go). They supersede pending state and use their own calendar reference. Successful lists/totals also clear pending state and use the current message's reference date. Genuine follow-ups use `answer_clarification` or `request_context=followup`, preserving known draft values. An explicit unsupported currency preserves a currency-correction draft without creating an expense: a bare number/yes keeps that question, an explicit RUB correction resumes it, and a new independent expense uses default RUB. A missing creation category defaults to `другое`; category clarification is reserved for an actual category change that lacks its desired value. Creation-category clarifications with a known amount use the fallback instead of asking another question. Invalid field answers preserve the validated draft; invalid independent operations cannot resurrect a superseded action. Cancellation requires a recognized standalone phrase and is harmless from idle; numeric/category replies never cancel. Cancellation clears only pending state, retaining the existing focus. Context expires after 30 minutes of inactivity, including focus and drafts; pending decisions also have a fixed deadline. Expired replies cannot restore a draft. Persistent conversation history is not required.

State changes, including activity timestamps, become visible in memory only after a confirmed commit of the response/expense transaction; expired states are ignored independently of transaction success. A known rollback retains the prior state. An uncertain commit matches `conversation.ErrCommitUncertain` and invalidates only the affected owner's transient state before another message can execute. Durable replies still replay by update ID; replay itself never clears newer state. Draft argument maps are copied before modification, including transaction retries. Safe structured conversation diagnostics contain only update correlation, allowlisted state/tool/clarification types, validation categories, transaction/delivery outcomes and reset/expiration reasons. They exclude raw text, prompts, arguments, amounts, comments, expense IDs and credentials.

## Selecting the Last Expense

1. If there is a current focus, use the selected record belonging to the user.
2. If there is no focus, including after context expiration or a restart, find the user's own record using `created_at DESC, id DESC`. The purchase date `spent_at` does not determine the most recently created record.
3. If the user has no records, report this without changing any data.
4. If the user stated a previous amount, compare it with the actual amount before making a change. Ask for clarification on a mismatch.
5. If an existing focus becomes stale because the record was changed, deleted, or reassigned through the panel, ask for clarification without silently replacing the selected expense.

Ownership and record freshness based on `updated_at` are checked atomically with the change. General calendar and conversation rules are in [requirements.md](requirements.md).

## Access and Write Invariants

- `user_id` is absent from model tool arguments: the server supplies it.
- Accept only known operations and fields. The LLM has no arbitrary SQL, HTTP requests, or administrative tools.
- All bot operations, including totals, last-record selection, and candidate searches, are scoped to the owner.
- Updates and deletes check `id` together with `user_id` directly in SQL.
- A missing record and another user's record produce the same «не найдена» result.
- Clarification selects a record only from the proposed candidates belonging to the user.
- Changing an expense and saving the Telegram message processing result occur in one transaction. Duplicate delivery to an allowed user returns the stored result without repeating the change.
- Success is confirmed after commit; failure to send a response does not repeat the change.
- The bot uses internal Go operations rather than the panel's open REST API.

## Startup and Operations

- Publish only the frontend reverse proxy's HTTP port on the trusted local network. PostgreSQL stays within Compose and uses a named volume.
- Apply migrations before starting the handlers.
- Internal `GET /readyz` checks PostgreSQL with a two-second deadline after migrations: empty 204 when available, generic 503 otherwise. Compose waits for this readiness check before starting nginx; nginx has a separate static-page healthcheck. Dependency failure marks the app unhealthy without restarting it. Telegram/LLM availability is not required for panel readiness, and nginx does not proxy this operational endpoint.
- In addition to the LLM and allowlist, configure the database connection, Telegram token, time zone, and HTTP port.
- Store secrets in `.env`; `.env.example` contains templates only.
- Bound external requests with timeouts. An LLM failure does not prevent the panel from working.
- An LLM error before execution does not change expenses. A committed result is not executed again.
- Parameterize SQL; do not enable unrestricted CORS. Mutating requests accept JSON and check `Origin` when present; an incompatible origin is rejected according to [api.md](api.md).
- These checks do not replace authentication: the API is available to any client within the accepted network boundary.
- Application and database availability checks and structured logs without keys, full conversation text, or expense contents are sufficient.
